# CLAUDE.md

Canonical context for AI assistants working in this repo. If anything elsewhere disagrees, trust this file.

## What this is
**ORA Navigator** — an AI assistant + proposal toolkit for Morgan State University's **Office of
Research Administration** (ORA): grants, compliance, pre/post-award, forms, ORA contacts, and a
guided workspace that helps inexperienced PIs actually write and submit fundable proposals.

## Three services
| Service | Stack | Local port | Container port |
|---|---|---|---|
| **frontend** | Vite + React 19 (PWA) | 3001 | 8080 |
| **backend** | FastAPI, **single-worker uvicorn** | 5002 | 5000 |
| **adk_agent** | Google ADK + Gemini 2.5 Flash (Vertex AI), `VertexAiSearchTool` over one unified KB datastore | 8081 | 8080 |

The chat path: frontend → backend (`vertex_agent.py`) → ADK agent (`adk_agent/ora_navigator_unified/`) → Gemini on Vertex AI. The backend also serves the proposal toolkit (below) and talks to Cloud SQL (MySQL) + Redis.

## Build / test / deploy
- **Backend tests (keep green before any push/deploy):**
  ```bash
  cd backend && JWT_SECRET=test-secret TRUSTED_HOSTS=testserver,localhost,127.0.0.1 \
    python3 -m pytest -q --ignore=tests/test_agent_instruction.py
  ```
  Env vars are required because importing `main` constructs the app. `test_agent_instruction.py` needs `google-adk` (not always installed locally). App-level e2e tests use FastAPI `TestClient` with `dependency_overrides` for `get_db` / `get_current_user` (see `tests/test_proposals_api_e2e.py`).
- **Frontend:** `cd frontend && npm run build` (no `node_modules`? `npm install` first). It's a **PWA** — verify changes in a fresh/incognito window.
- **Deploy: there is NO Cloud Build trigger — a merge to `main` ships NOTHING.** Confirmed again 2026-08-05: `gcloud builds list` showed no build since 2026-07-29 despite several merges, and production was still serving an image built hours before the code existed. Every deploy is submitted **by hand**:
  ```bash
  gcloud builds submit --config=cloudbuild.yaml . --substitutions=SHORT_SHA=$(git rev-parse --short HEAD)
  ```
  **The `--substitutions=SHORT_SHA=…` is REQUIRED on this config too, not just the scraper's.** `cloudbuild.yaml` interpolates `${SHORT_SHA}` in **9 places**, and it is populated only for repo-triggered builds — a local directory submit leaves it empty and the build dies instantly with `invalid image name ".../adk-agent:": could not parse reference`, naming a service rather than the missing substitution. This file previously gave the command without the flag, so the documented instruction failed on first contact. There's also a manual `deploy-cloudrun.sh` (needs local `gcloud`). **Always confirm a deploy actually ran** — `gcloud run services describe <svc> --region=us-central1 --format='value(status.latestReadyRevisionName)'` — rather than inferring it from a merge or a green build list. The **backend** runs `--min-instances=1 --cpu-boost` so the chat path never pays a 30–60s cold start (the dominant cause of slow first answers); the frontend stays `min-instances=0` (static, off the per-question path). **The ADK service MUST stay a SINGLE instance (`--min-instances=1 --max-instances=1`).** It stores agent sessions **in memory** (no `ADK_SESSION_DB_URI`), so with >1 instance a session created on one instance **404s on `/run_sse`** when the next call is routed to another — the user sees *"An error occurred while processing your question"*, intermittently (random per-instance routing). A brief bump to `--min-instances=2` for concurrency caused exactly this outage. **Never scale ADK horizontally without wiring a shared session store (`ADK_SESSION_DB_URI`) first.** `concurrency=80` lets one warm ADK instance handle normal + demo load fine. (You can apply a scaling change live without a full rebuild via `gcloud run services update <svc> --min-instances=N --max-instances=M`.) **`cloudbuild.yaml` is a single point of failure** — the backend deploy step is an inline bash heredoc, so a one-character typo there (e.g. a stray `=` swallowing `--min-instances`) breaks the *whole* deploy and silently blocks every merge from shipping. Validate it (`python3 -c "import yaml; yaml.safe_load(open('cloudbuild.yaml'))"`) after any edit.

With `roles/discoveryengine.viewer` alone (what `deploy-cloudrun.sh setup_iam` used to grant) reads work — the KB browser lists and searches fine — but every **Save 403s** with `discoveryengine.documents.update denied`, which reads as a UI bug rather than a permissions one. Editor covers `documents.create/.update/.delete`. Note this is a **project-level** grant and therefore broader than needed (it also allows datastore/engine create+delete); least privilege would be a custom role limited to `discoveryengine.documents.*`. Accepted deliberately — revisit if the project gains other Discovery Engine resources. `roles/discoveryengine.viewer` is now redundant alongside it. **`gcloud` may not be on `PATH` locally** — it lives at `~/google-cloud-sdk/bin/gcloud`.
- **Secrets** live in Secret Manager as `ora-database-url`, `ora-jwt-secret`, `ora-admin-email`, `ora-admin-password`, `ora-redis-url`, `ora-firecrawl-api-key`, plus **`SMTP_USER` / `SMTP_PASS`** (mapped in `cloudbuild.yaml`). Note the SMTP pair **breaks the `ora-*` naming convention** — they were created by hand on 2026-07-28 and replace the retired `ora-smtp`; don't "fix" the names without re-pointing `--set-secrets`. The Cloud Build runs as the **default compute service account** (`<projnum>-compute@…`), which lacks `secretmanager.secrets.create` — so the `deploy-backend` step **self-heals** `ora-firecrawl-api-key` (creates a `unset` placeholder if missing) so a missing optional secret never breaks the deploy. Create real secret values via the Console (the project picker prevents the "wrong project" mistake). **A hand-created secret has an EMPTY IAM policy** — the backend SA can't read it and the deploy fails outright. `SMTP_USER`/`SMTP_PASS` both needed an explicit grant: `gcloud secrets add-iam-policy-binding <name> --member=serviceAccount:oranavigator-backend@<proj>.iam.gserviceaccount.com --role=roles/secretmanager.secretAccessor`. The pre-existing `ora-*` secrets already carry this binding, which is why the omission isn't obvious.
- **`GOOGLE_GENAI_USE_VERTEXAI=TRUE`** must be set on the ADK **and** backend services (in `cloudbuild.yaml`) or Gemini falls back to the developer API and every call fails with "No API key was provided."
- **The KB scrape Job is built separately** — `gcloud builds submit --config=cloudbuild.kb-scraper.yaml . --substitutions=SHORT_SHA=$(git rev-parse --short HEAD)`, **not** from `cloudbuild.yaml`. Deliberate: the image is ~1.5GB (Playwright + Chromium), changes rarely, and putting it on the path every merge takes would slow every deploy and widen the blast radius of the file that already blocks all deploys when it breaks. **The `SHORT_SHA` substitution is required** — it's populated only for repo-triggered builds, so a local directory submit leaves it empty and the image tag becomes the invalid `kb-scraper:`. Two IAM grants are needed once, and **the second is the easy one to miss** — without it the admin button 403s while the run sits `queued` forever with nothing in the app logs: `roles/cloudsql.client` on the project for the backend SA, and `gcloud run jobs add-iam-policy-binding oranavigator-kb-scraper --region=us-central1 --member=serviceAccount:oranavigator-backend@<proj>.iam.gserviceaccount.com --role=roles/run.jobsExecutorWithOverrides`. **That role, NOT `roles/run.invoker`** — this file and `cloudbuild.kb-scraper.yaml` both said `run.invoker` until 2026-07-29 and it was wrong. `run.invoker` grants `run.jobs.run` but **not** `run.jobs.runWithOverrides`, and `kb_scrape_service.py` passes a container override to inject `SCRAPE_RUN_ID`. The backend SA already holds `run.invoker` **project-wide**, so following the old instruction granted nothing and left the identical 403 — a fix that looks applied and changes nothing. `roles/run.developer` also works but carries ~80 permissions including `run.services.delete`; the scoped role is exactly three (`run.jobs.run`, `run.jobs.runWithOverrides`, `run.executions.cancel`).
- **The scrape engine is Playwright + Chromium (`kb_scraper/crawler.py`), the default since 2026-08-03.** A headless browser reads each page, so there is **no model in the read path**: no refusals, byte-stable text, and the accordions get expanded. Measured against the live site 2026-08-03, before any code change: **21/21 pages readable, including all 18 the Gemini engine refused** (the whole of research-compliance, budget development, the internal routing form, the PI handbooks, `/ora`); the same page read three times gave an **identical hash** (`fanda-cost-rates` 1540 chars, `iacuc-sops` 3102 chars, three times each); the IACUC SOPs page yields **50 `SOP n.n:` entries**, confirming `_expand_accordions()` reaches content absent from the served HTML; ~2.9s/page median, so a 59-page crawl is ~3 min against the 3600s task timeout. Because the text is byte-stable **the fingerprint gate is live** — only pages that actually moved cost a model call, where the old engine re-adjudicated everything every run. Playwright also **discovers links**, so pages with no KB document surface as `new` proposals (a genuine content-gap inventory; expect a batch on the first run). `gemini-3.6-flash` is still the **adjudicator** — only page-reading changed.
- **The Gemini reader is still available as `--engine=gemini` / `SCRAPE_ENGINE=gemini`, and its limits are why it is no longer the default.** `kb_scraper/gemini_crawler.py` sends each URL to the model with `"tools":[{"urlContext":{}}]` and asks for a markdown **extraction**. Three measured properties: **(1) 26 of 59 ORA URLs (44%) come back EMPTY with `finishReason: RECITATION`** — the safety filter for reproducing source material. The blocked set is the compliance core: *all* of research-compliance (human subjects, animal research, COI, research security, NSPM-33, RCR, Maryland ethics), most of pre-award (budget development, internal routing form, proposal components, PI role), post-award reporting, the PI handbooks, and `/ora` itself. Under this engine those pages are **not monitored**. The readable 33 are the brochure pages (About, Mission, Announcements, Staff Directory, Funding Sources). Prompt wording matters: "reproduce the full text verbatim" is blocked on nearly every page, "extract into markdown" on 44%. **(2) A RECITATION block is reported UNREADABLE, never as an empty or deleted page** — same invariant as `looks_unreadable()`, and the most destructive bug this job could have. **(3) The extraction is NOT byte-stable** — one unchanged page read three times at temperature 0 measured 1444/1466/1478 chars, three different hashes — so `resolve_audit()` forces `--audit` for this engine rather than leaving a gate in place that silently claims every page moved every run. Under it, quote grounding verifies against the model's own extraction rather than the page, which is weaker than golden rule 2 gives you on Playwright. **It calls REST, not the google-genai SDK** — this image pins `google-genai==1.14.0` to match `backend/requirements.txt` and 1.14.0 has no `url_context` field on `types.Tool`.
- **Fingerprints are engine-specific (`KbPageFingerprint.engine`).** A fingerprint hashes the extracted page **text**, and the two engines extract the same unchanged page differently, so a hash is only a valid baseline for the engine that wrote it. `load_baseline()` filters by engine and `upsert_fingerprint()` stamps it; a row from the other engine — or a pre-migration `NULL` — reads as a **first sighting**, which records the hash and proposes nothing. Two consequences worth knowing: this is what makes switching engines a silent re-baseline instead of ~59 bogus "changed" proposals, and it scopes the **removed-page sweep** (`prior` minus the URLs seen this run) so a switch doesn't propose that every previously-known URL was deleted from the site. **`url` stays `unique=True`**, so there is one row per page and switching engines overwrites rather than preserving a per-engine baseline — which is why both write paths upsert: a bare INSERT raises `IntegrityError` on a page the other engine already saw. Added with the usual self-healing migration in `init_db()` (golden rule 5).
- **`SCRAPE_ENGINE` was set BY HAND on the live Job, and the repo does not show it.** `cloudbuild.kb-scraper.yaml` does not mention `SCRAPE_ENGINE` — but the deployed Job carried `SCRAPE_ENGINE=gemini` as an env var (observed 2026-08-03 on execution `…-dlccm`), set by someone running `gcloud run jobs update` after the 2026-07-29 deploy. **An env var beats the code default**, so changing the default in `build_parser()` and shipping it would have changed nothing, silently — the Job would have kept using Gemini while the code, the tests and the docs all said Playwright. What saves it is that line 107 of the yaml uses **`--set-env-vars`**, which *replaces* the whole environment set rather than merging, so a deploy through that file clears the hand-set value. Two rules follow: **never reason about this Job's configuration from the repo alone** (`gcloud run jobs executions describe <exec>` prints the env actually used), and **never "fix" line 107 to `--update-env-vars`** — that would preserve the stale override forever.
- **The scraper's Gemini model is pinned separately from every other caller.** `SCRAPE_MODEL=gemini-3.6-flash` + **`SCRAPE_MODEL_LOCATION=global`**, both read only by `kb_scraper/adjudicator.py` (the location falls back to `GOOGLE_CLOUD_LOCATION`, so no other caller moves). Adjudication is offline batch work over ~59 pages where judgment quality matters and latency doesn't — the opposite of the chat path, which stays on `gemini-2.5-flash` in `us-central1`. **The location override is required, not a preference:** `gemini-3.6-flash` **404s in `us-central1`** and answers only on the `global` endpoint (verified by direct `generateContent` calls). Because a model failure falls back to "not material" (golden rule 3), getting this wrong makes every adjudication 404 and the run reports **zero changes and looks like a clean crawl**. `thinking_config(thinking_budget=0)` is accepted by 3.6-flash and bills no thinking tokens (verified), so the existing anti-truncation setting carries over unchanged.

## Golden rules (followed everywhere; keep following them)
1. **AI is advisory; the deterministic core is authoritative.** Numbers, pass/fail, and eligibility verdicts are computed by code — the LLM only explains, drafts prose, outlines, or gives advisory feedback. It can never change a figure.
2. **Ground every AI claim.** Any "covered/strong" finding must quote the source text; unquotable claims are dropped (`_verify_evidence` in `draft_critic.py` / `section_coach.py`). The membership check **collapses whitespace on both sides** (`" ".join(s.split())`) — a pasted/hard-wrapped draft has newlines where Gemini's quote has spaces, and a raw substring match would wrongly reject a real quote and mark a complete section "NOT FOUND".
3. **Graceful fallback.** Every AI path returns a deterministic result when Gemini is unavailable (`gemini_client.generate_json/text` return `None` → caller falls back). Never error because the model is down.
4. **Human reviews before commit.** Extractions and budgets are returned for review; nothing is saved until the user confirms.
5. **Conventions:** structured data stored as **TEXT columns + `json.dumps/loads`** (e.g. `Submission.budget_json`, `compliance_json`, `sections_json`, `notes`). New columns are added with a **self-healing migration** in `main.py:init_db()` (try `SELECT col`; on error `ALTER TABLE ADD COLUMN`) — safe on prod MySQL, no Alembic.
6. **One feature = one focused change.** Don't refactor unrelated code. Verify before claiming done.
7. **Never push automatically.** Do NOT run `git push` (and don't open PRs) on your own — only when the user explicitly asks in that message. Pushing to `main` triggers the Cloud Build deploy, so an unrequested push ships to production. Committing locally is fine to stage work, but wait for an explicit "push"/"deploy" before it leaves the machine. Approval to push once does not carry over to later changes.

## The Proposal Toolkit (backend `services/` + per-proposal modals in `frontend/src/components/`)
Each proposal (`Submission` + `SubmissionTask` in `models.py`, logic in `proposals_service.py`, sponsor task templates in `proposal_templates.py`) has a toolbar of tools:

- **Solicitation ingestion** — `solicitation_extractor.py` (PDF→text via pdfplumber → Gemini → contract dict with `source_quotes`; fabricated quotes flagged via `_verify_source_quotes`). Two entry points: upload a PDF, or **paste a URL** (`url_fetcher.py`). The URL fetcher is SSRF-guarded (resolve + reject private/loopback/link-local IPs, pin the validated IP to defeat DNS rebinding). Some funder sites (NSF/Akamai) **block cloud-datacenter IPs**, so a direct fetch falls back through a scraper chain: **Firecrawl** (`_fetch_via_firecrawl`, preferred — runs a real browser from non-blocked IPs; needs `FIRECRAWL_API_KEY`, and treats the `unset` deploy-placeholder as no-key), then `r.jina.ai` (set `JINA_API_KEY`), then `allorigins`. Uploaded PDFs are 100% local (pdfplumber) and never hit an IP block. `create_submission_from_solicitation` seeds the checklist; multi-category deadlines are surfaced via `deadline_details`. The extracted **eligibility text** is stored in `notes` and fed to the Drafting Coach.
- **Budget Helper** — `budget_helper.py`: deterministic F&A/MTDC/fringe math (Morgan's real rates), sponsor-cap check. **Coaching layer:** `budget_advisories()` (sanity flags), `suggest_trims()` (concrete cuts to get under cap), category/F&A/fringe tooltips. **v2:** multi-year projection with escalation (`compute_budget` detects `project_years`; single-year output unchanged), CSV export (`budget_to_csv` + `/budget.csv`), per-line justification, and a **deterministic prose** budget justification (`draft_justification` — labeled paragraphs, reads like a real submission). AI only polishes the prose and is forbidden to change figures; the `/api/budget/justification` endpoint falls back to the template when the AI output is empty **or truncated** (missing the total-cost figure — a Gemini-under-load failure mode). The UI **effort→person-months helper is read-only**, derived from each person's `effort_pct` in the People rows (not a separate input), so it can never disagree with the budget. **Per-category caps:** when a solicitation defines multiple proposal categories with different award maxima (e.g. NSF IDSS Category I/II/III), `solicitation_extractor` returns `budget_cap_details` (`[{category, cap}]`, a stated **range → max**), persisted as a `Category caps:` line in `notes` (round-tripped by `reconstruct_solicitation_context`; category names sanitized of `;`/em-dash); the single `budget_cap` stays the smallest. The modal shows a **Funding category** picker that fills the Sponsor cap — default is a blank "Select your category…" so the PI consciously picks; the picker appears only for 2+ categories. **Spreadsheet view:** `compute_budget` also returns a render-ready `table` (`{columns, rows}`; single-year = one `Amount` column, multi-year = a column per year + `Total`) built by `_budget_table` from the per-year breakdowns (now retained instead of discarded). The modal renders it as a read-only **Budget table** grid — it formats numbers but computes none, so it always matches the summary and the CSV (row order mirrors `budget_to_csv`). **Modal layout:** the Budget table's `<table>` uses class **`bh-table`** — NOT `bh-grid`, which is the form's two-column `display:grid` and silently turned the table into a broken 2-column grid (thead/tbody split, amounts clipped). The whole modal body (form + summary + table + justification) scrolls as **one** `.bh-scroll` region; the navy **Summary is `position:sticky`** so the total stays in view while the taller form scrolls (disabled on mobile). The **justification draft panel has a Close (×)** that clears `justification`+`perLine` without closing the whole modal. **v3 (multi-year coaching):** the multi-year path is otherwise unchanged but now *explains itself* to a first-time PI — `ESCALATION_GUIDANCE` tooltip (escalation hits **salaries only**, ~2-3% federal norm; exposed via `rate_options()`), per-year **salary deltas** in `multi_year.years` (`salary_delta`/`salary_delta_pct`, shown as "salary +$X (Y%)"), the cap badge spells out it's the **cumulative N-year TOTAL** (`multi_year.cap_basis="cumulative"`), `draft_justification` adds a **"Period of performance"** paragraph (figures from `multi_year`; placed *before* the final total so the endpoint truncation guard still trips), and `multi_year_advisories()` flags **0% escalation** (info) / **>10%** (warn) — appended to `advisories` at the `compute_budget` level since `_compute_single` never sees `escalation_pct`. All additive/deterministic; AI still only polishes. Out of scope (deliberately): per-person escalation rates and ramp-up/down spending profiles.
- **Drafting Coach** — `section_coach.py`: per-section **outline** + advisory **feedback** on the PI's own draft (covered/missing elements, grounded). Coaching only — never writes prose. Section menu is **by sponsor** (`_SPONSOR_ORDER`: NSF → Project Summary / Project Description / Broader Impacts / Data Management Plan; NIH → Specific Aims / Research Strategy / DMP; else generic). **v2:** save drafts (`sections_json`), live length meter (`WORD_TARGETS`), "match THIS solicitation" (feeds required attachments/eligibility/page limits), deterministic `clarity_check()`. **v3 (solicitation-aware):** `outline_section` now USES the solicitation context it already received — outline tips reflect this funder's page limits/required attachments/eligibility, tailoring runs on **topic OR context** (not just topic), and the "match THIS solicitation" panel shows in **outline** mode too; `SECTION_SAMPLES` maps each section to an authored **Sample Proposals Library** entry (validated via `get_sample` so a link can't 404), surfaced as a "See a worked example" link in both modes; `review_section` (via `_REVIEW_SYSTEM`) also flags solicitation requirements the draft doesn't address (evidence-grounding unchanged). **v4 (reviewer-lens + cross-section coherence):** **(A)** a deterministic per-sponsor `REVIEW_RUBRICS` / `review_rubric(sponsor)` — the panel's actual scoring criteria (NSF Intellectual Merit + Broader Impacts; NIH Significance/Innovation/Approach/Investigators/Environment; generic fallback) — is attached to **both** outline and review results (so the PI writes TO the rubric), and `review_section` asks for advisory `reviewer_notes` (one per criterion, "how a panel would judge THIS draft"). Notes are **opinions/questions, NOT coverage claims** (no quote required); coverage stays in the grounded `checklist`. Notes are filtered to valid criteria; empty when AI is off (rubric always present). **(B)** `coherence_check(sponsor, drafts, context, budget)` — a NEW advisory check that compares the PI's *saved* sections against each other: NIH Specific Aims ↔ Research Strategy, scope ↔ eligibility, timeline ↔ budget (`_coherence_candidate_pairs` builds only the pairs whose source sections exist). Every `"aligned"` verdict must quote **both** sides, verified with the shared `_quote_in()` helper (the whitespace-collapse match, **refactored out of `_verify_evidence`** — golden rule 2); unverifiable → demoted to `"unclear"`, quote dropped. Deterministic fallback when AI is off (incl. an Aim 1/2/3 label co-occurrence pass; never fabricates quotes). `ready:false` when <2 sections saved or no pair applies. Endpoint **`POST /api/me/submissions/{id}/coherence`** (reads existing `sections_json`/`budget_json`/`notes` — no new state); UI is a third **"Cross-section"** tab gated on ≥2 saved drafts, plus a `ReviewerPanel` rendered in outline+review. **v5 (solicitation responsiveness matrix):** `responsiveness_matrix(sponsor, drafts, context)` — a NEW whole-proposal advisory check that maps each explicit solicitation **ask** onto the PI's *saved* drafts, attacking the #1 triage reason (non-responsiveness). The requirements list is assembled **deterministically** by `_responsiveness_requirements` from already-grounded state — page-limited named sections (`context["page_limits"]` keys → `SECTIONS` labels), required attachments/elements (`context["required_attachments"]`), the sponsor's `review_rubric()` criteria, and eligibility text — **so the AI can never invent an ask** (it receives a fixed `id` set and only assigns coverage). Status vocabulary is `addressed | partial | not_found | check_by_hand` (draft_critic's `missing|unclear` renamed) — **coverage only, never a score/verdict** (respects the removed-Fundability boundary below). Every `addressed`/`partial` must quote a saved draft verbatim, verified with `_quote_in`; unverifiable → demoted to `check_by_hand`, quote dropped, and `where` is re-attributed authoritatively to the section containing the verified quote (not trusted from the model). Deterministic fallback marks every row `check_by_hand` (never guesses `not_found` — offline it can't prove absence — and never fabricates a quote). Dedupe by normalized label (DMP as both attachment + page-limited section collapses to one, section wins). Endpoint **`POST /api/me/submissions/{id}/responsiveness`** (reads `sections_json`/`notes` — no new state, no budget); UI is a fourth **"Responsiveness"** tab gated on ≥1 saved draft. **UI removed (2026-07):** the **Cross-section** (v4 coherence) and **Responsiveness** (v5) tabs were removed from the Drafting Coach UI by product decision — the Coach now offers only "Outline it" and "Feedback on my draft". Both **backend endpoints (`/coherence`, `/responsiveness`) and services remain** (now unused by the UI); re-add the tabs to restore them.
- **Draft Critic vs Drafting Coach** — different jobs: the **Coach** grades the *writing* of one section; the **Critic** (`draft_critic.py`) checks the *whole package's completeness/compliance* (required sections & **solicitation-required attachments**, page limits, budget vs cap) + advisory AI review. Completeness is the Critic + the solicitation checklist, never the Coach.
- **Guided steps** — `task_guidance.py`: keyword-matched how-to + sample per checklist task, attached in `_submission_task_to_dict`; per-task "add to calendar".
- **Guided Proposal Pathway** (the proposal detail view in `MyProposals.jsx`, presentation/orchestration — **no new tool logic**) — for inexperienced PIs, the flat toolbar is a **staged path**: Set up → Build → Review & submit, each tool carrying a ✓ status badge from serializer flags (`has_budget`/`has_compliance`/`has_sections` = `bool(sections_json)`; Solicitation from the `hasSolicitation` notes-regex; Critique is stateless). A pure `nextStep(submission)` picks the single recommended action — only that button gets the accent (the rest share one calm style) — and a plain-language **"What to do next"** card explains the current step + why (active proposals only). Delete + Add-to-Calendar live in a `⋯` overflow. The summary shows the **internal ORA routing deadline** (`proposals_service.internal_routing_deadline` → `internal_deadline` field, **5 business days before** the sponsor date, weekends skipped) so a first-timer plans backward from the real institutional cutoff.
- **Draft Critic** (`draft_critic.py`) — mechanical pre-submission checks (page limits, required sections/attachments, budget vs cap) + advisory AI review.
- **Compliance Sentinel** (`compliance_sentinel.py`) — IRB/IACUC/COI/RCR/export rules. **Deadline Watcher** (`deadline_watcher.py`) — AI-personalized reminder emails (cron). `ics_export.py` — calendar feeds.

**Removed:** the former **Fundability / Eligibility self-check** tool (reviewer-lens scoring + go/no-go) was deleted per product decision — `services/fundability.py`, `services/eligibility.py`, their tests, the `FundabilityModal`, and the `/fundability/criteria` · `/eligibility` · `/fundability` endpoints are gone. ## KB web scrape (`kb_scraper/` — a Cloud Run **Job**, not backend work)
Admin clicks **Run scrape**; a Job crawls `morgan.edu/office-of-research-administration` with Playwright, and documents whose page materially changed are updated automatically and flagged for review.

**Why a Job.** All three of these bite and none are optional: the backend has **CPU throttled outside requests** (no `--no-cpu-throttling` anywhere) so a detached asyncio task stalls the moment the response closes; **`--timeout=300`** kills any single request and a full crawl is ~20 min (measured ~3s/page); and **`--max-instances=20` with no session affinity** makes in-process job state invisible to whichever instance serves the next poll — the **exact failure class that took the ADK service down**. So the work runs in a Job (CPU for its whole life, 3600s task timeout) and **all state lives in Cloud SQL** (`ScrapeRun`, `ScrapeChange`, `KbPageFingerprint`), polled every 2s. **Progress is polled, not SSE** — an SSE stream would hit the same 300s cap mid-crawl.

**Detection is a fingerprint gate, then AI.** The stored `content` is an **LLM summary of a page, not the page text**, so the two can never be diffed directly — comparison is scrape-to-scrape against a stored SHA-256 of the normalized text. Only moved hashes reach Gemini, which judges material vs cosmetic and drafts the replacement. A material verdict **must quote the live page verbatim**, verified in code with the same whitespace-collapsing test as `section_coach` (golden rule 2); unquotable or low-confidence is demoted to review and **never applied**.

**An unreadable page is NOT a change.** 404, empty JS render, timeout, or a 404 body served with a 200 → `looks_unreadable()` → the document is **left alone** and reported separately. Treating a failed read as "the content was deleted" is the single most destructive thing this feature could do.

**Nothing is applied automatically any more (2026-07-29).** The Job **never** modifies a document — not content, not metadata. Every material change becomes a `pending` row in `scrape_changes` and the document moves only when an admin clicks **Approve**; the tree's badge is a render-time join on pending rows, so an unapproved proposal leaves no trace on the document. It also **does not adjudicate a page's first sighting** — the stored `content` is an LLM summary written in May, so comparing it to live text would mark essentially every page "material" and propose rewrites of correct documents; first sighting records the fingerprint and `--audit` opts into the full sweep deliberately. Verified on the first real prod run: `changes_found=24`, **`changes_applied=0`**, zero rows with `status=applied`, zero rows carrying `previous_content`. The auto-apply paragraph below describes the **approve** path, which is what still writes.

**Approval is bounded and reversible.** `previous_content` is stored on every applied change and revert is one click. The review flag (`needs_review`, `last_auto_updated`, `what_changed`) goes in **`struct_data`, never in `content`** — Vertex indexes `content`, so a disclaimer written there could be quoted back to a PI asking about F&A rates. The tree renders an amber ⚠ badge with recursive `review_count` per node.

**Measured reality — only ~7% of the KB is auto-updatable.** 383 documents derive from just **59 distinct morgan.edu URLs**: 28 URLs map 1:1 (28 documents, auto-applicable) and 31 URLs feed 2+ documents (**355 documents**), because the KB was built by *splitting* pages — the IACUC SOPs page became **52** documents, D-RED seminars **49**, IACUC forms **37**. Re-splitting a changed page back across 52 documents unattended would corrupt all of them, so multi-document pages are **always reported, never rewritten**. Treat this feature as a change *reporter* that auto-applies where it safely can.

**`start_run` reaps stale runs** (>90 min without progress → `failed`). Without it a crashed Job — OOM, image pull failure, the missing `run.jobsExecutorWithOverrides` binding — leaves a row stuck in `running` and the one-at-a-time guard locks the feature permanently with no way back except a DB edit.

## ORA eTraining modules (Articulate Rise) — `backend/kb_structured/_etraining_modules.json`

**8 modules, 347,397 characters, 106 knowledge checks, 52 embedded files.** Verified complete: a residual audit against the raw course payload found **1,426 prose strings, 0 missing — 100%**. Extracted 2026-08-05 after ORA asked whether the modules were in the KB. They were not: the KB held a **300–660 character description** of each ("a module about travel exists") and nothing they teach. This is Morgan's own grant-spending procedure, authored by ORA, and it exists nowhere else in the KB — not on the website pages, not in the PDFs.

**Rise ships the whole course to the browser in one payload.** The lesson sequence and the quiz gate are UI controls, not server-side ones, so the full text is one request per module. **Two endpoints are needed** because ORA's share links come in two shapes and only one host answers each:

```
share.articulate.com/{id}       ->  POST /api/instant-links/{id}/course
rise.articulate.com/share/{id}  ->  GET  /api/rise-runtime/boot/share/{id}
```

Attachments live on `articulateusercontent.com/{key}` (the `attachment.key` field), verified downloading.

**Gemini cannot read these pages and never will.** Measured with the URL Context tool: `URL_RETRIEVAL_STATUS_SUCCESS`, `finishReason: STOP`, **10 characters returned — the word `UNREADABLE`**. Not a safety block, not a fetch failure; the content simply isn't in the HTML. A real browser gets the cover page (~2.1k chars) and still not the lessons. **Only the course API works.**

**Three traps that cost real content, all found by re-checking rather than by the first pass:**

1. **Proofpoint-wrapped links.** The e-training page links several modules through `urldefense.proofpoint.com/v2/url?u=…`, which no `articulate.com` match will catch. Decoding (`-3A`→`:`, `-2D`→`-`, `-5F`→`_`, `_`→`/`) exposed **3 modules the KB had no record of**.
2. **The KB's links are STALE.** Republishing a Rise course mints a new share ID, and the KB kept the old one. `Purchasing with Purpose` is the bad case: the KB pointed at a **superseded 28k module** while the site links a rewritten **97k** one with different lessons (Uniform Guidance Subpart E, procurement thresholds). Always read the share IDs off the live `/trainings/e-training` page, never from `procedure_url`.
3. **A naive walker drops the load-bearing bits.** Requiring a space in a string kills single-word headings — *Allowability, Allocability, Reasonableness, Consistency*, the four cost principles. Skipping the `media` key kills labeled-graphic markers, which is where the procurement thresholds `$0 - $5,000` / `$5,001 - $25,000` live. That was ~134k characters, a third of the total.

**Multiple-choice answers MUST be rendered with the correct one marked.** This is a correctness rule, not a formatting one. The modules teach through worked problems whose distractors are plausible dollar figures — `$40,000` and `$18,410` sit beside the correct `$21,040` and `$17,431`. Flattened to prose, the assistant can quote a **deliberately wrong** number as Morgan policy. Every option carries `[CORRECT ANSWER]` or `[incorrect]`, with per-answer feedback.

**Loading:** `scripts/load_rise_etraining.py` (`--dry-run` / `--revert`). Content-only via `update_document`, so `struct_data` — placement, `procedure_url`, titles — is untouched; the previous bodies are written to `_etraining_kb_backup.json` first. The JSON is committed so the load is reproducible and the content reviewable in a diff.

**Blocks are self-contained — there is no nested content to chase.** `interactive`, `interactive-fullscreen` and `multimedia` blocks carry their items inline; a scan for iframes, embeds and Storyline packages found **zero** outbound content references. Everything is in the one payload.

**Rise stores answer explanations under THREE keys** — `feedback`, `feedbackCorrect`, `feedbackIncorrect` — and a quiz may use any of them. Reading only `feedback` silently dropped the teaching ("Try again. Remember the distinction between direct and indirect costs.") from every module.

**Not captured:** video narration (no transcripts), **466 screenshots and diagrams** (images, not text — the Banner and Purchasing modules lean on them heavily, so a "which field do I fill in" answer may still be incomplete; OCR or a vision model would be needed), and the contents of the 52 attachments (linked, not read). **Known risk:** these documents are far larger than any other in the KB (one is 97k chars) and the datastore cannot be configured for chunking, so each is retrieved whole. If answers on these topics come back vague, split each module into per-lesson documents — the extraction already has the lesson structure.

## Caching (layers + lifetimes)
Caching exists to dodge the two real latency costs — the **Gemini call** and the **networked Cloud SQL read** from a **single-worker** backend — NOT to cache authoritative figures. **Cache the expensive (LLM answers), never the authoritative (budgets, statuses, verdicts, deadlines).**

**Chat answer cache** — `cache.py`, a 3-tier stack behind `query_cache.get/set` (keyed `md5(normalized_query : model)` — **no `user_id`**, so it's shared across users; personal/recall questions are gated out by `_should_cache`):
- **L1** in-memory (`cachetools.TTLCache`) — **24h**, 500 entries, per-instance.
- **L2** Redis — **7 days**, shared across instances, persistent. Degrades gracefully to "no L2" if Redis is down.
- **L3 semantic** (Google `text-embedding-004`, 256-dim) — matches re-worded questions at **cosine ≥ 0.95**; 100 in-memory entries + a 7-day Redis copy.
- **Citations** ride the same tiers under a `cit:` key (L1 24h / L2 7 days) so a cache HIT re-emits Sources.
- The chat HTTP responses are **`Cache-Control: no-cache`** (the cache is server-side only).

**Other server caches:** popular questions (`popular_questions.py`, in-process **6h** + Redis 7 days, daily-cron refreshed; the welcome-screen chips are now the **actual most-asked real user questions, Gemini-polished** — typos/grammar/semantic rewrite — and **PII-filtered** (`_is_personal_or_junk` drops SSN/salary/email/greetings/recall), NOT a fixed 36-question pool; `DEFAULT_QUESTION_POOL` is only the safe fallback/top-up. The one Gemini polish call runs on the daily refresh, never on a page load), Open Grants samples (`ogrants_finder.py`, **6h** TTLCache), forms catalog (`forms_catalog.py`, `@lru_cache` — **process-lifetime**, until redeploy). **Browser:** PWA service-worker precache of the app shell (workbox `autoUpdate` — until next deploy), Google-Fonts runtime `CacheFirst` (**1 year**), and `localStorage` (token/theme — until logout). TTLs are hard-coded constants per file (not yet env-configurable).

**Never cached:** personal-recall answers, errors/outages, transient "busy/try again" text, refusals (all gated in `cache.set`), and any answer's **personalized greeting** (stripped before storage — see Load-bearing fixes).

## Load-bearing fixes (don't regress)
- **Gemini 429 on the chat path** (`vertex_agent.py`): a quota error arrives as response *text*; `_is_rate_limited` detects it, retries with backoff, then flags an outage — instead of laundering it into "system is busy" and amplifying via Pass-2 regeneration.
- **Two lanes — social chat (LANE 1) vs ORA (LANE 2)** (`agent.py` `BASE_INSTRUCTION` + `vertex_agent.py`): every chat message is either **LANE 1 social chat** (Gemini answers it itself, no KB) or **LANE 2 an ORA question** (answer ONLY from the KB). The `agent.py` instruction names both lanes explicitly; when a message could be either it must be treated as **LANE 2 and searched** — Gemini is FORBIDDEN to answer a possible ORA fact from its own training/memory (the strict "never fabricate a rate/deadline/name/ID" grounding preamble). **LANE 1** ("hi", "how are you", "thanks", "very good", "bye", plus bot-directed remarks like "do you miss me", "are you real?", "who are you") gets a warm KB-free reply — NOT the "I can only help with ORA" refusal, and NOT the "developed for Morgan State / ora.inavigator.ai" identity blurb (that blurb is only for "who made this app"). LANE 1 is answered by Gemini **naturally, to the message actually sent** — the per-kind example replies are now TONE guidance, not scripts. Do NOT re-add a fixed responder or force every pleasantry into one template (an earlier `smalltalk_reply()` fixed-per-category responder was removed as robotic; fix wording in the instruction instead). A substantive NON-ORA *knowledge* question (trivia, coding, recipes, other schools) is NOT LANE 1 — it is still refused per SECURITY. **Routing (`skip_kb_search`):** `_do_agent_pass` sets `state_delta["skip_kb_search"] = _is_smalltalk(msg) or _is_personal_identity(msg)`, and `agent.py`'s `before_model_callback` (`_select_model`) **drops the `VertexAiSearchTool` + KB prefetch** for those turns so the model physically can't run a stray KB search (which used to staple bogus Sources onto a greeting/identity turn). `_is_smalltalk` (whole message is pleasantry tokens via `_SMALLTALK_RE`, **OR** a bot-directed social question via `_SOCIAL_QUESTION_RE`) feeds BOTH this routing AND the Layer-3 verdict override (a LANE 1 turn is never graded "weak" and regenerated into a refusal) AND the `_is_non_kb_reply` Source-strip. Kept **NARROW**: `_is_personal_identity` (name/dept/role/email) and `_SOCIAL_QUESTION_RE` must NOT match institutional "my F&A rate" / "do you know the UEI?" — those stay LANE 2 and KEEP their KB search + Sources.
- **Evidence whitespace** (`section_coach.py` / `draft_critic.py`): `_verify_evidence` collapses whitespace before the substring match — see golden rule 2.
- **Grounded citations from the real KB search** (`vertex_agent.py` + `agent.py` + `kb_prefetch.py`): a *correct but uncited* chat answer was the symptom of the model answering from the **prefetched KB context** (injected into the instruction) instead of the native `VertexAiSearchTool` retrieval, so `groundingMetadata` came back empty (no Sources) AND it tripped the weak-grounding verdict (the slow Pass-2 regeneration). Two-part fix: **(B)** the prefetch block is now labeled **`[REFERENCE CONTEXT - FACT-CHECK ONLY]`** (was "use this to ground your answer") + grounding **rule 8** in `BASE_INSTRUCTION`, so the answer + Sources rest on the model's own KB search. **(C)** `_fallback_citations(query)` runs a live Vertex AI Search over the same unified datastore and resolves titles → URLs via `_get_kb_url_map()`, attached at the DELIVER step when a *trusted* ORA answer came back uncited — gated by `_wants_fallback_citations()` (skips small talk, refusals, outages, `kb_fail`, already-cited). Forcing the retrieval tool is **not** possible: `vertex_ai_search` is native retrieval grounding, and `tool_config mode=ANY` governs only `function_declarations`. (You *can* still guarantee a search happens — by calling `SearchServiceClient` yourself, which `_fallback_citations` already does — you just cannot compel the model to call its own tool.)
- **Layer 1 prefetch now computes real TF-IDF** (`kb_prefetch.py`): the scorer was named TF-IDF in nine places but had **no IDF term** — `(tf/doc_len) * qf * 2.0` weighted a word in 189/382 docs (`research`) the same as a word in one. It now multiplies by `_idf(term) = log(N/df)`, with `_document_frequencies()` building the DF index once per cache load (memoized on `_cache_ts` + doc count, own `_df_lock` so it never nests with `_cache_lock`). A term in every doc scores 0; a term in one of 382 scores ~5.9. Measured against the 324 question→doc pairs in `eval/per_doc_results.jsonl`: **recall@5 90.4% → 91.7%**, 9.2ms/query. Tests: `backend/tests/test_kb_prefetch.py` (loads the module **by file path** — importing the package pulls `agent.py` → `google-adk`, which isn't always installed, which is why `test_agent_instruction.py` is excluded from the standard run). **Deliberately NOT changed:** the `[REFERENCE CONTEXT - FACT-CHECK ONLY]` wording (a test now asserts it survives) — relabelling it as a grounding source is what emptied `groundingMetadata` in the first place. Two known bigger levers left alone: the title bonus at `kb_prefetch.py:189` is a **substring** match (`"st(rate)gy"` matches the query token `rate`, worth +3) while the tokenizer uses word boundaries; and `category`/`subcategory` are loaded into the cache (`dict(doc.struct_data)`) but **never read by the scorer**, which only builds `f"{title} {content}"`. An offline bench combining BM25 + those labels measured **96.3%** recall@5, so most of the remaining headroom is there, not in the TF weighting — the flat `+10` entity / `+3` title bonuses still decide 94-99% of the score mass.
- **Chat latency budget** (`vertex_agent.py`): a turn can stack a full **Pass-2 regeneration** on Pass-1. `_over_latency_budget(elapsed)` (`CHAT_LATENCY_BUDGET_S`, code default 7s, **set to 5s in prod via `cloudbuild.yaml`**) skips the second agent round-trip when a *usable* Pass-1 answer graded weak and the turn has spent its budget — deliver Pass-1 + caution note instead (empty Pass-1 still regenerates; the streaming path already skips Pass-2). A `[LATENCY]` per-turn log (ms + verdict + chunks) makes the <10s target measurable. The bigger lever is warm instances (see Deploy) — cold starts, not the pipeline, were the ~40s.
- **Layer 3 grounding verification — surgical re-grounding REMOVED** (`vertex_agent.py` `_run_verified` / `_run_verified_stream`): the weak-answer path is now **grade (coverage ≥ 50% backed → "ok"; chunk count is NOT a gate) → LANE 1 / personal-recall guard (ship as-is) → latency bail (over budget → ship Pass-1 + `_WEAK_NOTE`) → strict-regenerate once (`_STRICT_PREFIX`, KB-only) → refuse (`_REFUSAL_MSG`)**. The streaming path can't regenerate, so a weak streamed answer just appends `_WEAK_NOTE`. **The UI only ever takes the streaming path** — `App.jsx` loads `Chatbox.jsx` → `/chat/stream` → `_run_verified_stream`; the non-streaming `Chat.jsx` is imported nowhere, so **the Pass-2 / `_REFUSAL_MSG` ladder is unreachable from the app** and `_run_verified` serves only `query_agent` callers (e.g. `/chat/guest`). On the live path Layer 3 is a **post-hoc annotator, not a gate**: the answer is already on screen, and all it can still do is append `_WEAK_NOTE`, strip or attach Sources, add the staff-name disclaimer, and inject procedure links (the terminal `done` event's text replaces the streamed preview in `Chatbox.jsx`). The former **surgical per-sentence re-grounding** (`_unsupported_sentences` / `_surgical_reground` + grounded-span math + identifier-rejection, ~220 lines) was **deleted** — it fired **0 times in 148 production turns** (measured with `scripts/analyze_layer3_logs.py`, which parses the `[LAYER3]`/`[LATENCY]` logs). **Do NOT re-add it.** `_check_identifier_faithfulness` stays (still called by `_finalize_answer` for logging; the user-facing footer remains disabled), as do the coverage gate `_evaluate_grounding` and the latency bail.
- **The coverage gate: what it measures, and who it actually applies to** (`vertex_agent.py` `_do_agent_pass` + `_evaluate_grounding`). Three things about Layer 3's only numeric signal that are NOT obvious from reading either function alone:
  - **`coverage` is not "% of the topic covered"** — it is `grounded_chars / len(answer)`, the fraction of the *answer's characters* falling inside Gemini's self-reported `groundingSupports` spans. It measures **citation density, not completeness**, and it is asserted by the model being graded (nothing compares a span's text to the chunk's text — that's the separate, log-only `_check_identifier_faithfulness`). A thorough answer that adds correct context beyond the retrieved passage scores *lower*, not higher. Spans are summed without an interval merge, so overlapping supports would double-count and `coverage` can exceed 1.0.
  - **Chunks-without-supports fails closed (fixed 2026-07-23).** When `groundingChunks` come back but `groundingSupports` is empty, nothing was measured. That branch used to set `coverage = 0.5` and log it as "conservative" — but the gate is `coverage >= _GROUNDING_MIN_COVERAGE` (**0.5**), so it cleared the bar on the `>=` boundary *every time*, silently claiming a verification that never ran. It now scores **0.0** → grades `weak`. Regression tests: `test_chunks_without_supports_score_zero_coverage` / `test_real_supports_still_compute_a_real_coverage` in `tests/test_grounding.py` (they drive the real SSE parser via the `_drive_pass` harness). **Don't restore the 0.5.**
  - **The gate does not run for authenticated users at all.** `_evaluate_grounding` returns `"ok"` on `has_attached_context` **before** it reaches the coverage comparison; `has_attached_context` is `bool(context)`, `context` is the `USER PROFILE (from account)` block, and `get_current_user` (`deps.py`) rejects any token lacking an email — so `profile_parts` is never empty and the coverage check is **dead code on `/chat` and `/chat/stream`**. It only bites on **`/chat/guest`** (`context=""`). Treat "Layer 3 verifies grounding" as **guest-only** until that bypass is narrowed (the fix would be scoping `has_data` to *uploaded file content* rather than any profile string — a real behavior change that would start grading production answers; deliberately not done). Related: **`_GROUNDING_MIN_CHUNKS = 2` is a dead constant** — defined, documented, and read by nothing since `df161ca`. It was never an AND-requirement even when live; the original gate was `chunks >= 2` **OR** `coverage >= 0.3`, i.e. two sources was a *sufficient* pass route, never a necessary one. When that branch was deleted (Gemini reports the chunk count unreliably — the same flakiness that forced `_fallback_citations` to exist) the coverage bar was raised 0.3 → 0.5 to compensate.
- **`update_document` used to erase metadata on any read failure** (`datastore_manager.py`): the read-modify-write swallowed **every** exception into `data = {}` and then patched that over `struct_data`, silently wiping `title`, `category`, `kb_path` and `file_path` on one transient blip. The document still saved, still answered questions, and just lost everything that placed it. Now **`NotFound` alone** is a legitimate create (`allow_missing=True`); any other read failure **refuses to write** — a failed save is recoverable, a wiped document is not. Regression tests in `tests/test_datastore_metadata.py`. This was latent for a long time and became a real hazard only when bulk placement writes arrived.
- **`upload_document` invented categories and crashed on PDFs** (`datastore_manager.py`): it guessed `category` from the same dead `academic|career|financial` prefix list, so **every** upload landed as `"general"` with the doc_id repeated as its subcategory; and it eagerly `utf-8`-decoded the bytes into an **unused** variable, raising `UnicodeDecodeError` on a `.pdf` — a file type the endpoint explicitly accepts — before the handler's error path could catch it. It now writes no placement at all, so an upload surfaces under **Unfiled** where it is visible and one click from filed. A wrong label is worse than none.
- **Write paths didn't invalidate the listing cache** (`main.py`): upload and delete cleared `query_cache` but not `_cloud_kb_cache`, so a newly uploaded document was invisible to both the flat list and the tree's Unfiled bucket for up to 60s — exactly the "where did my document go" the tree exists to prevent.

Related and worth knowing: **the seeded documents carry no `source_url` in `struct_data`** (`setup_kb_datastore_v8.py` writes `doc_id/title/category/subcategory/source_file/file_path/playwright_verified` and stops), which is why the scraper's URL→document index reads the snapshot and uses `struct_data` only as an overlay. ## Known limitations / open work
- **NSF (and similar Akamai sites)** block server-side URL fetches by IP. **Firecrawl** (set `FIRECRAWL_API_KEY`, free tier ~500 one-time credits) is the reliable path; the Jina/allorigins fallbacks are throttled from Cloud Run. Locally the direct fetch works (residential IP isn't blocked). Uploaded PDFs always work regardless.
- Drafting-coach AI tailoring/feedback quality depends on the deployed Gemini being healthy; it degrades to deterministic checks otherwise.
- Demo aids live in repo root: `ORA_Navigator_Demo_Script.pdf`, `Sample_Solicitation_for_Demo.pdf` (generated by `scripts/make_demo_pdfs.py`).
- **Vertex AI Search runs on pure defaults, and most knobs are unreachable from the chat path.** `agent.py` builds `VertexAiSearchTool(data_store_id=UNIFIED_KB_ID)` — datastore ID and nothing else — and the only `SearchRequest` in the repo (`vertex_agent.py:530`, the citation fallback) sets just `serving_config`/`query`/`page_size`. Verified live against `oranavigator-kb-v8`: **no Engine/app exists** (`engines` → `{}`), **no materialized ServingConfig** (`GET .../servingConfigs/default_search` → 404; search works only because `default_search` is *implicit*), no Controls, no custom models. Consequences: **(a)** synonym maps (the "subrecipient ≈ subaward" fix) require a Control attached to a serving config, so they are **unreachable without first creating a search app** — do not plan on them as a config tweak; **(b)** extractive answers/segments and `summary_spec` are **Enterprise/engine-level** and fail closed today (`FAILED_PRECONDITION`, `LLM_ADDON_NOT_ENABLED`); **(c)** `chunkingConfig` cannot be enabled after datastore creation and doesn't support `text/plain`, so `searchResultMode: CHUNKS` would need a **new datastore**. What DOES work now, unused: `filter` (bare field path — `category: ANY("...")`, **not** `structData.category`), `boost_spec` (±1, verified reordering), `content_search_spec.snippet_spec` (real snippets on Standard edition), `relevance_threshold` (10/10/5/4 results at LOWEST/LOW/MEDIUM/HIGH), `relevance_score_spec` (per-result 0–1 score — a real external signal, unlike Gemini's self-reported `coverage`). The live `default_schema` already marks every `struct_data` field indexable/searchable/filterable (except `title`, a `keyPropertyMapping`), so **no schema patch is needed** first. Two ceilings: the genai `VertexAISearch` type exposes only `datastore`/`engine`/`data_store_specs`/`filter`/`max_results` (so the **chat path can never use boost, snippets, thresholds, or scores** — only the direct `SearchServiceClient` path can), and `google-cloud-discoveryengine==0.13.5` is pinned while `relevanceThreshold`/`relevanceScoreSpec`/`rankingExpression` only exist in newer clients (current 0.20.2).
- **The KB is deliberately non-redundant — never gate an answer on "N sources".** Facts live on exactly one page, mirroring morgan.edu/ora's nav. Measured: the off-campus F&A rate (`26%`) and the instruction rate (`64%`) each appear in **exactly one** document; `54%`/`53%` in two. So a hard "must be backed by ≥2 sources" rule would **reject correct answers** about single-source facts. This is also why `_GROUNDING_MIN_CHUNKS = 2` was retired: when live it was `chunks >= 2` **OR** `coverage >= 0.3` (a *sufficient* pass route, never a requirement). If a source count is reintroduced, keep it an **OR**, and count distinct resolved citations — not Gemini's self-reported `result["chunks"]`, which is unreliable.
- **`BASE_INSTRUCTION` grounding rule 5 instructs a tool that does not exist.** `agent.py:378` tells the model to *"call `list_kb_topics` FIRST"* with detailed path examples, but `agent.py:476` registers `tools=[unified_kb]` only — `list_kb_topics` is imported and never wrapped in a `FunctionTool`, deliberately (the comment at `agent.py:473` records the Gemini API constraint: you cannot mix `VertexAiSearchTool` with `FunctionTool` in one agent). Safe to delete rule 5's tool references.
- **Two copies of the KB metadata, and nothing syncs them.** The live **Vertex AI Search datastore** (`oranavigator-kb-v8`) is what the chatbot searches and what the admin dashboard edits. `backend/kb_structured/` is a **static snapshot committed to the repo**, read at import and cached for the process lifetime — it powers the **Forms catalog** (`forms_catalog.py` reads `_all_documents.jsonl`, 383 rows), `_get_kb_url_map()` (citation title→URL, now with a live overlay — see Load-bearing fixes), `kb_tree.py` (tree shape + curated titles), `kb_browser.py`, the scraper's URL→document index, and `proposal_templates.py`. Refreshing the snapshot requires regenerating the JSONL and redeploying the backend.
